# 中山市空间数据知识图谱方案（业务优先 + 体现 KG 优势）

## 1. 文档目标

本方案用于指导 `data/company/zhongshan.sqlite` 的知识图谱构建，满足两类目标：

1. **业务查询优先**：围绕真实业务问题，保证“查得到、查得准、查得快”。
2. **体现知识图谱优势**：在多跳关联、语义统一、路径解释和规则推理上显著优于关系型数据库直查。

---

## 2. 数据集特征与建模原则

### 2.1 数据集特征

- 来源：中山市空间数据 SQLite（17 张表，含 POI、标准地址、行政区划、警务辖区、道路路口、设施等）。
- 特点：
  - 显式外键约束缺失，存在大量“语义外键”（如 `S_DM`、`S_CJDM`、`GADM`、`ZDGADM`）。
  - 空间字段 `geom` 为 EWKB Hex，点/线/面混合。
  - 地址层级和辖区层级天然适合图结构表达。

### 2.2 建模原则

- **先问题后建模**：先定义业务问题模板，再反推节点和边。
- **主干优先**：先做稳定主干关系，再扩展细分语义。
- **关系优先于属性完备**：优先保证跨表路径可达。
- **可解释优先**：关键归属关系必须可回溯路径证据。

---

## 3. 业务优先的目标图谱结构

## 3.1 核心实体层

- `AddressUnit`：门牌、栋、单元、房间等地址对象（`zs_MP_bz`、`zs_DH_bz`、`zs_DY_bz`、`zs_FJ_bz`、`zs_YL_bz`）。
- `Place`：POI/AOI/设施/路口（`zs_POI_dm`、`zs_AOI_dm`、`zs_facility_dm`、`zs_roadcross_dm`）。
- `AdminRegion`：市-镇街-社区-街路层级（`zs_city_bz`、`zs_town_bz`、`zs_community_bz`、`zs_street_bz`）。
- `Jurisdiction`：公安局-分局-派出所-警务室（`zs_GAJ_xq`、`zs_GAFJ_xq`、`zs_PCS_xq`、`zs_JWS_xq`）。

## 3.2 主干关系层（第一优先级）

- `belongsToAdminRegion`：地址/POI/设施 -> 行政区。
- `belongsToJurisdiction`：对象 -> 警务辖区。
- `hasParentRegion`：行政层级（社区 -> 镇街 -> 市）。
- `hasParentJurisdiction`：警务层级（警务室 -> 派出所 -> 分局 -> 公安局）。
- `associatedWithAddressUnit`：POI/设施与标准地址对象关联。
- `locatedOnStreet`：对象与街路/路口关联。

## 3.3 扩展关系层（第二优先级）

- `nearby`（空间近邻，阈值可配置）。
- `sameCategoryAs`（语义分类统一后形成）。
- `sameCodeAs`（跨表业务编码对齐）。

---

## 4. 关键字段策略（业务查询导向）

### 4.1 主键与业务键双轨制

- 内部主键：优先 `gid`（保证唯一与稳定）。
- 业务检索键：`DM`、`DZBM`、`XZQHDM`、`GADM`、`ZDGADM`。
- 展示与查询优先使用业务键，`gid` 仅用于技术层 ID。

### 4.2 RAG 映射忽略字段（避免语义噪声）

下列字段不进入术语映射候选：

- `geom`
- `gid`
- `S_GUID`
- `Shape_Length`
- `Shape_Area`

说明：这些字段要么是技术字段、要么是几何度量字段，不适合作为业务语义属性参与 RAG 映射。

### 4.3 分类统一

- 统一 `DLMC / ZLMC / XLMC / FLDM / FLMC / SSLX` 到业务分类字典。
- 建立“标准分类节点”，通过 `inCategory` 关系挂接各来源对象。

---

## 5. 突出 KG 优势的能力设计

## 5.1 多跳关联查询能力

将“地址-行政-辖区-POI/设施”链路显式化，支持 2~6 跳稳定查询。

示例：

- 某派出所辖区 -> 覆盖社区 -> 覆盖街路 -> 门牌 -> 关联 POI/设施。

## 5.2 语义统一查询能力

对跨表异名同义字段进行标准化，使“同一业务概念”可一次查询命中多数据源。

## 5.3 路径解释能力

查询结果返回关系路径（为何属于该辖区/行政区），增强可解释性与业务可信度。

## 5.4 规则推理能力

基于规则补全隐式关系（如层级归属、跨表关联），并保留 `confidence` 以控风险。

---

## 6. 与关系型数据库对比的评测框架

## 6.1 评测原则

- 对比公平：RDB 侧允许建索引与优化 SQL。
- 重点对比“复杂问题可答率”，不仅是单次查询耗时。

## 6.2 指标体系

- 复杂问题可答率（能否稳定写出并执行）。
- 查询时延（P50/P95）。
- 查询复杂度（SQL JOIN 数量 vs 图查询跳数）。
- 可解释性（是否可返回可读路径证据）。
- 需求变更成本（新增关系时改造量）。

## 6.3 题型配比建议

- 20%：简单单表查询（基线对照）。
- 50%：多跳跨域查询（重点体现 KG 优势）。
- 20%：跨表语义统一查询。
- 10%：规则推理与路径解释查询。

## 7. 工程实施路线（结合当前项目）

1. **术语与映射阶段**
  - 使用 `data/company/zhongshan_rag_terms.json`。
  - 应用“RAG 忽略字段”策略，减少误映射。
2. **关系增强阶段**
  - 先应用高置信语义键关系（覆盖率阈值建议 >= 95%）。
  - 对推断关系打 `confidence`，低置信关系入候选层。
3. **图谱生成阶段**
  - 输出 TTL（主产物）。
  - 按需导入 Neo4j 进行图查询评测。
4. **评测闭环阶段**
  - 维护“KG 优势题库”。
  - 周期化输出可答率、时延、解释性报告。

## 8. 里程碑建议

- M1（1 周）：完成主干实体 + 一级关系落图，产出首版 TTL。
- M2（1~2 周）：完成分类统一与空间关系预计算，形成可评测图谱。
- M3（1 周）：完成 RDB vs KG 对比评测与报告。

---

## 9. 成果验收标准

- 业务主问题（预定义模板）可答率 >= 90%。
- 一级关系覆盖率 >= 95%，低置信关系可追溯。
- 复杂问题（多跳）在 KG 侧查询表达更短、解释更完整。
- 输出可复现实验报告（含 RDB 对照与路径样例）。
